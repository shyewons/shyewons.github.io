## 이 프로젝트에서 얻은 것

이번 프로젝트에서 가장 크게 배운 것은 **LLM이 자연스러운 답변을 만드는 것과, 그 답변을 웹서비스에서 사용할 수 있게 만드는 것은 다른 작업이라는 점**이다.

Ollama 앱에서 광고 문구를 생성하는 것 자체는 어렵지 않았다. 하지만 웹 화면에 결과를 나누어 보여주려면 일정한 응답 구조가 필요했고, 입력에 없는 제품 특성을 덧붙이거나 이모지 금지 지시를 따르지 않는 문제도 있었다. 모델이 응답하는 동안 사용자가 기다릴 수 있는 화면과, 생성에 실패했을 때의 안내도 필요했다.

그래서 상품 정보를 입력하면 제목·본문·CTA·해시태그를 생성하고 복사할 수 있는 작은 광고 생성기를 만들었다. FastAPI와 Ollama를 연결하고, 그 사이에 입력 검증·구조화 출력·후처리·오류 처리를 붙였다.

완성한 핵심 흐름은 다음과 같다.

```text
상품 정보 입력
→ FastAPI 요청 검증
→ 프롬프트 구성
→ Ollama 광고 생성
→ JSON 응답 후처리
→ 출력 모델 검증
→ 결과 카드 표시와 복사
```

아직 광고의 사실성을 자동으로 보장하는 서비스는 아니다. 대신 **입력 형식이 맞는지, 출력 구조가 맞는지, 내용에 근거가 있는지를 서로 다른 문제로 바라보게 됐다.** 이전 게시판 프로젝트에서 프론트와 백엔드 사이의 데이터 이동을 배웠다면, 이번에는 그 흐름 안에 LLM을 넣었을 때 추가로 다뤄야 하는 문제를 경험했다.

하루짜리 학습 프로젝트로 시작했고, 구현 과정에서는 Codex의 도움을 받았다. 낯선 코드의 역할을 질문하고, 직접 요청을 보내 오류와 생성 결과를 확인하며 진행했다. 아래에는 그 과정에서 이해하게 된 내용을 정리했다.

## 1. 광고 생성과 결과 확인에만 범위를 맞췄다

처음부터 로그인이나 DB를 붙이지는 않았다. 이번에 확인하고 싶었던 것은 상품 정보가 프롬프트로 전달되고, 모델의 응답이 다시 화면에 표시되는 과정이었다.

입력은 상품명, 특징, 타깃 고객, 광고 채널, 말투의 다섯 가지로 정했다. 출력은 제목, 본문, CTA, 해시태그로 나눴다. 화면에는 입력 폼과 결과 카드, 복사 버튼을 두었다.

로그인·DB·RAG·Agent·결제는 제외했다. 기능을 늘리기보다 하나의 요청이 끝까지 처리되는 흐름을 먼저 연결하기 위해서였다.

파일도 처음부터 전부 만들지 않았다. `main.py`와 폴더를 먼저 만들고, 입력 모델이 필요할 때 `schemas/ad.py`, 모델 호출을 연결할 때 `services/ad_generator.py`를 추가하는 식으로 진행했다. 파일 이름을 외우기보다 각 파일이 필요한 이유를 이해하고 싶었다.

## 2. FastAPI, httpx, CORS의 역할부터 구분했다

Ollama 연결 방법을 알아보는 과정에서 `httpx`가 등장했다. 이전에 `ChatOllama`로 모델을 호출해본 적이 있었기 때문에, 새로운 라이브러리를 직접 사용해야 하는 이유가 궁금했다. FastAPI에서 사용하던 `CORSMiddleware`와의 차이도 헷갈렸다.

역할을 나누니 이해하기 쉬워졌다.

| 구성 요소 | 이번 프로젝트에서의 역할 |
| --- | --- |
| FastAPI | 브라우저 요청을 받고 응답을 제공하는 서버 |
| HTTP 클라이언트 | 서버에서 Ollama 같은 다른 서버로 요청을 보내는 도구 |
| ChatOllama | Ollama 호출을 LangChain 방식으로 다루는 연결 객체 |
| CORSMiddleware | 다른 출처의 브라우저 요청에 대한 CORS 허용 정보를 제공하는 미들웨어 |

결국 익숙한 `ChatOllama`로 호출을 구성했다. 별도의 `httpx.post()` 호출 코드를 작성하지 않아도 됐다. 이후 오류 처리에서는 내부 통신에 사용되는 `httpx`의 예외와 타임아웃 설정을 다뤘다.

화면도 FastAPI에서 함께 제공했다. 브라우저는 같은 출처의 `/ads/generate`로 요청하므로 이 구성에서는 별도 CORS 설정을 추가하지 않았다.

## 3. 검증 클래스가 어떻게 작동하는지 이해했다

먼저 `AdRequest`로 입력 구조를 정의했다.

```python
class AdRequest(BaseModel):
    product_name: str = Field(min_length=1, max_length=100)
    features: str = Field(min_length=1, max_length=1000)
    target: str = Field(min_length=1, max_length=200)
    channel: str = Field(min_length=1, max_length=50)
    tone: str = Field(min_length=1, max_length=50)
```

처음에는 클래스에 `return`이 없는데 검증 결과를 어떻게 판단하는지 궁금했다. `request: AdRequest`라고 적으면 함수 안에서 검증하는 것인지도 명확하지 않았다.

FastAPI는 이 타입 선언을 보고 **라우트 함수를 실행하기 전에 요청을 검증한다.** 검증을 통과하면 `AdRequest` 객체를 만들어 함수에 전달하고, 실패하면 422 응답을 보낸다. 성공 여부를 `True`로 받는 구조가 아니라, 검증된 객체를 받거나 오류가 발생하는 구조였다.

```text
요청 JSON
→ AdRequest 검증
  ├─ 성공: 객체를 라우트 함수에 전달
  └─ 실패: 422 응답
```

이후 `AdCopy`에는 `headline`, `body`, `cta`, `hashtags`를 정의했다. 같은 Pydantic 모델이지만 `AdRequest`는 들어오는 데이터, `AdCopy`는 내보낼 광고 데이터의 기준이었다.

## 4. 두 번의 오류로 입력과 출력 검증의 차이를 확인했다

첫 번째는 Swagger에서 요청을 보낼 때 발생했다. 요청 내용을 Python에서 인자를 전달하듯 작성했다.

```text
product_name="데일리 텀블러"
```

서버에는 JSON을 보내야 했으므로 다음처럼 작성해야 했다.

```json
{
  "product_name": "데일리 텀블러",
  "features": "350ml, 스테인리스 소재",
  "target": "직장인",
  "channel": "인스타그램",
  "tone": "친근하게"
}
```

이때의 `json_invalid` 오류는 상품명 길이가 잘못된 문제가 아니었다. 요청 자체를 JSON으로 읽지 못해 입력 모델 검증에 도달하지 못한 상태였다.

두 번째는 `ResponseValidationError`였다. 라우트에 `response_model=AdCopy`를 지정했지만, 함수에는 처음 입력 확인용으로 작성한 코드가 남아 있었다.

```python
def generate_ads(request: AdRequest):
    return request.model_dump()
```

FastAPI는 제목·본문·CTA·해시태그를 기대했는데, 실제로는 상품명·특징·타깃 등이 반환됐다. 그래서 광고 필드 네 개가 없다는 오류가 발생했다.

반환 부분을 광고 생성 함수 호출로 바꿨다.

```python
def generate_ads(request: AdRequest):
    return generate_ad_copy(request)
```

이 요청에서는 LLM이 잘못된 답을 준 것이 아니라, **서버가 잘못된 종류의 데이터를 반환하고 있었다.** 오류가 입력을 읽는 단계인지, 모델 생성 단계인지, 최종 응답 검증 단계인지 구분해야 한다는 점을 배웠다.

## 5. 자연스러운 광고가 입력에 충실한 광고는 아니었다

Ollama 앱에서 먼저 데일리 텀블러 광고를 생성했다. 제공한 특징은 `350ml`, `스테인리스 소재`, `손잡이 있음`이었다.

그런데 결과에는 다음 표현이 포함됐다.

- “가볍고 튼튼하고”
- “프로필 링크에서”
- “손목에 무리가 덜 가요”

구매 경로는 입력하지 않았고, 제품 무게나 신체 부담에 대한 정보도 없었다. 이후 코튼 가방 테스트에서는 크기 정보 없이 “넉넉한 수납공간”이라는 표현이 나왔다.

이 과정에서 소재 자체에 대한 일반적인 설명까지 막아야 하는지도 고민했다. 스테인리스의 일반적 특성을 설명하는 것과, 특정 텀블러의 위생성이나 내구성을 보장하는 것은 다르다. 입력에 없는 말이 나왔다고 전부 거짓이라고 단정할 수도 없지만, 그렇다고 제품에 대한 근거가 확보된 것도 아니다.

그래서 결과를 평가할 때 **허위로 확인된 주장과 입력으로 확인되지 않은 주장을 구분해야 한다**고 생각하게 됐다. 프롬프트에는 입력에 없는 제품 성능이나 효과를 단정하지 말라는 규칙을 보강했다. 다만 규칙을 추가해도 항상 지켜지는 것은 아니었다.

## 6. 구조화 출력과 후처리를 서로 다른 단계로 나눴다

이전에 사용했던 체인은 모델 응답을 문자열로 받는 방식이었다.

```python
chain = prompt | model | StrOutputParser()
```

광고 생성기에서는 화면의 각 카드에 들어갈 데이터를 구분해야 했다. 그래서 JSON Schema를 전달하는 구조화 출력을 사용했다. 후처리까지 추가한 최종 구성은 다음과 같다.

```python
structured_model = model.with_structured_output(
    AdCopy.model_json_schema(),
    method="json_schema",
)

chain = prompt | structured_model
```

프롬프트에서 이모지와 마크다운을 금지했는데도 제목에 이모지가 남고, 본문에 `**강조**`가 나오는 경우가 있었다. 화면은 일반 텍스트를 표시하므로 마크다운 기호가 그대로 보였다.

이를 서버 후처리로 정리했다. 일반적인 이모지와 마크다운 기호를 제거하고, 공백을 정리하고, 해시태그 중복과 개수를 제한했다. 화면에서만 제거하면 API를 직접 사용하는 쪽에는 정리되지 않은 결과가 전달되므로 서버에 두었다.

여기서 검증 순서도 바꿨다. 엄격한 길이·개수 검증이 먼저 실행되면, 초과한 응답을 후처리할 기회가 없었다. JSON Schema를 딕셔너리로 전달해 응답을 받은 뒤, 정리하고 최종 검증하는 순서로 구성했다.

```text
구조화된 JSON 응답
→ 텍스트·해시태그 후처리
→ AdCopy 최종 검증
```

정리 후 제목처럼 필수 문구가 비어 버리면 정상 광고로 반환하지 않고 출력 형식 오류로 처리한다.

다만 이 작업은 표현 형식을 다듬는 것이지 사실 검증은 아니다. 이모지를 제거할 수 있다고 해서 “가볍다”라는 표현의 근거까지 판단할 수 있는 것은 아니다.

## 7. 기다리는 화면에도 설명이 필요했다

입력 폼과 결과 카드가 연결된 뒤에는 또 다른 문제가 보였다. “광고를 작성하고 있어요”라는 문구만 있으니, 화면이 멈춘 것인지 실제로 기다리는 중인지 알기 어려웠다.

실제 진행률이나 평균 시간 기반 로딩 바를 생각했지만, 현재 응답 방식으로는 모델이 언제 생성을 끝낼지 알 수 없었다. 임의로 100%를 채우는 대신 움직이는 로딩 바와 경과 시간을 표시했다.

경과 시간은 타이머 실행 횟수를 세지 않고 `performance.now()`의 차이로 계산했다. 성공하거나 실패하면 `finally`에서 타이머를 정리하고 생성 버튼을 다시 활성화했다.

이 표시는 모델 내부의 진행률을 증명하지는 않는다. 대신 **사용자가 요청을 보낸 뒤 얼마나 기다렸는지**는 알려준다. 화면에 보여줄 수 있는 정보와 추정에 불과한 정보를 구분하는 선택이었다.

## 8. 같은 500 오류로 보이던 실패를 나눴다

처음에는 생성 중 예외가 발생하면 화면에서 서버 오류 정도만 확인할 수 있었다. 연결 실패와 출력 형식 오류는 대응 방법이 달라서 구분하기로 했다.

모델 호출 쪽에서는 예외를 내부 오류 코드로 바꾸고, 라우터에서 HTTP 상태 코드와 안내 문구로 변환했다. 프런트엔드는 그 문구를 표시한다.

| 상황 | 처리 |
| --- | --- |
| 요청 JSON·입력 검증 실패 | 422 |
| Ollama 연결 실패·모델 미설치 | 503 |
| 통신 대기 시간 초과 | 504 |
| 모델 출력 형식·처리 오류 | 502 |
| 예상하지 못한 서버 오류 | 500 |

이 과정에서 사용자 정의 예외도 살펴봤다.

```python
class AdGenerationError(Exception):
    def __init__(self, code: str):
        self.code = code
        super().__init__(code)
```

`Exception`이 부모 클래스이고, `super().__init__(code)`는 부모의 예외 초기화 기능을 호출한다. `self.code`는 우리가 분류에 사용할 속성이다. 예전에 배운 클래스 상속이 실제 오류 처리 코드에서 어떻게 사용되는지 연결해 볼 수 있었다.

## 9. 자동 테스트와 직접 확인한 결과를 구분했다

텀블러·플래너·가방 정보를 넣어 결과를 비교했다. 친근한 말투나 대학생 대상 표현은 나타났지만, 문자 메시지용 광고도 길게 생성됐고 제품 특성을 추론하는 표현이 남았다. 말투를 반영하는 것과 채널에 맞는 길이·내용을 보장하는 것은 별개의 문제였다.

오류 분류와 후처리에는 자동 테스트도 추가했다. 현재 7개 테스트 메서드에서 정상 응답, 입력 검증, 예외별 응답, 텍스트 정리, 후처리 후 빈 문구의 거절을 확인한다.

이 테스트에서는 모델 응답을 모의한다. 따라서 **테스트 통과는 오류 처리와 정리 로직의 동작을 확인한 것이지, 실제 광고 품질을 보장한 결과는 아니다.** 실제 모델의 출력은 별도로 읽고 확인해야 한다.

## 다음 단계

이번에는 광고 생성부터 결과 확인까지 한 흐름을 연결하는 데 집중했다. 현재 길이 제한은 초과한 문자열을 잘라내므로 문장이 끊길 수 있고, 채널별 길이 정책도 없다. 후처리는 모든 마크다운과 이모지를 처리하는 완전한 파서가 아니며, 의미 있는 상품 표기에 영향을 줄 수도 있다.

추가로 개선한다면 문장 단위 길이 조정과 채널별 제한부터 다루고 싶다. 입력에 없는 사실적 주장을 어떻게 검증할지도 별도 과제로 남겼다. 자동 재시도는 아직 구현하지 않았다.
